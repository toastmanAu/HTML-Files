Build a Nervos CKB Live Block Mining Visualizer

Create a polished, fully functional web application that connects directly to a user-configured Nervos CKB node over WebSocket, subscribes to new tip headers, displays an animated mining sequence while waiting, and shows a special success image whenever a new block arrives.

The project must run as a static HTML application without a backend.

Required Output

Build the complete application using:

* index.html
* embedded CSS and JavaScript, or optional separate local CSS/JavaScript files
* no build process
* no framework
* no server-side component
* no placeholder code
* no pseudocode
* no TODO comments
* no omitted implementations

The page must work when served from a simple local static server.

The project root will contain these transparent 1024×1024 PNG assets:

mine_0.png
mine_1.png
mine_2.png
mine_3.png
mine_4.png

Do not generate, replace, rename, embed, or modify these images.

⸻

Core Purpose

The application represents the process of waiting for a new Nervos CKB block.

While connected and subscribed:

1. Repeatedly animate mine_0.png through mine_5.png.
2. Continue looping those six frames while waiting for the next block.
3. When a new tip-header subscription notification arrives:
    * immediately stop or pause the mining loop;
    * display mine_found.png;
    * animate the result prominently;
    * update all block and chain information;
    * keep the success image visible for a configurable but sensible period, approximately 2–4 seconds;
    * then return to the six-frame mining loop while waiting for the next block.

The animation must not accelerate or create multiple overlapping timers after reconnecting.

The user must be able to configure:

* host or IP address
* WebSocket port

Provide sensible defaults suitable for a local node, but do not assume that every node uses the same WebSocket port.

An example endpoint may look like:

Clearly explain in the interface that the configured CKB node must expose WebSocket RPC and permit access from the browser’s origin.

Provide:

* Connect button
* Disconnect button
* Reconnect button
* Save endpoint button
* Reset-to-default button

Persist the endpoint settings in localStorage.

Never automatically transmit data anywhere except to the endpoint selected by the user.

CKB Subscription

After the WebSocket opens, send this JSON-RPC request:

{
  "id": 1,
  "jsonrpc": "2.0",
  "method": "subscribe",
  "params": ["new_tip_header"]
}

Do not mark the application as successfully subscribed merely because the socket opened.

The state progression must distinguish:

Disconnected
Connecting
Socket Connected
Subscribing
Subscribed
Reconnecting
Error

Only show Subscribed after the node returns a successful subscription ID.

Store the returned subscription ID.

Handle new-header notifications shaped like:

{
  "jsonrpc": "2.0",
  "method": "subscribe",
  "params": {
    "result": "...",
    "subscription": "0x..."
  }
}

CKB subscription implementations may return params.result as either:

* an already parsed JavaScript object; or
* a JSON-encoded string containing the header object.

Implement a safe parser that supports both forms.

Reject malformed notifications gracefully without breaking the socket connection or animation loop.

Confirm that the notification’s subscription identifier matches the currently active subscription when one is available.

Unsubscribe and Cleanup

Before a deliberate disconnect, attempt to unsubscribe using the active subscription ID.

Use the correct CKB unsubscribe JSON-RPC structure supported by the connected node. If unsubscribe is unsupported or fails, close the WebSocket cleanly anyway.

On disconnect:

* stop animation timers;
* stop refresh timers;
* clear pending reconnect timers;
* clear the active subscription ID;
* prevent stale WebSocket event handlers from altering current state;
* close the socket;
* update the interface immediately.

Use connection-generation IDs or equivalent logic so events from an old socket cannot corrupt a newer connection.

⸻

Initial State and Duplicate Detection

A connection can be established immediately before or during a block change. Avoid treating the initial fetched tip as a newly discovered block.

After connection:

1. Request the current tip header.
2. Record its hash and block number as the baseline.
3. Subscribe to new_tip_header.
4. Treat a notification as a new block only if its block hash differs from the last processed tip hash.

Deduplicate repeated notifications by block hash.

If the same header arrives twice, update neither the new-block counter nor the success animation twice.

Handle a possible chain reorganisation sensibly:

* if a new header has the same or lower height but a different hash, label it as a possible reorg;
* do not crash;
* update the displayed canonical tip information;
* record the event in the local event log.

Hexadecimal and Numeric Parsing

CKB JSON-RPC commonly returns numeric values as hexadecimal strings prefixed by 0x.

Create reusable helpers to:

* safely identify valid CKB hex numbers;
* convert small values to JavaScript Number only when safe;
* use BigInt for large values;
* format large integers with separators;
* retain and display the original hexadecimal value;
* avoid precision loss;
* handle malformed or missing fields.

Do not use:

parseInt(value, 16)

for arbitrarily large blockchain values and then assume the result remains precise.

For timestamps:

* interpret the header timestamp correctly as milliseconds since Unix epoch;
* show local date and time;
* show ISO time;
* show relative age such as 18 seconds ago.

Update relative-time labels once per second without making an RPC call every second.

⸻

Epoch Parsing

The header’s epoch field is a packed CKB epoch representation, not an ordinary decimal epoch number.

Implement a helper that decodes the packed epoch value using BigInt.

Expose:

* epoch number
* block index within epoch
* epoch length
* percentage through the epoch
* remaining blocks in the epoch

Validate the decoded values before displaying them.

Also compare the decoded tip-header epoch information with get_current_epoch when that RPC method is available.

If the returned structures disagree, show both values and add a non-fatal diagnostic warning instead of silently overwriting one.

New Block Presentation

When a genuinely new block notification arrives:

1. Record the arrival time using performance.now() and Date.now().
2. Stop the normal mining frame progression.
3. Display mine_found.png.
4. Show a prominent message such as:

NEW BLOCK FOUND

5. Display:
    * human-readable height;
    * shortened hash;
    * exact arrival time;
    * block timestamp;
    * difference between local receipt time and block timestamp.
6. Apply a tasteful success animation:
    * scale pulse;
    * glow;
    * brief particle-like CSS effect if performant;
    * no canvas dependency required.
7. Play no audio unless the user explicitly enables it.
8. After the success period, return to mining mode.

If another block arrives while the success image is still visible:

* process it immediately;
* update to the latest block;
* restart the success-display duration;
* do not queue stale animations;
* increment the session block counter once per unique hash.

Polling Fallback and Health Checks

The main mechanism must remain the WebSocket new_tip_header subscription.

Optionally implement a conservative health check that:

* periodically calls get_tip_block_number over the existing WebSocket;
* confirms that the connection is responsive;
* does not replace subscription-based detection during normal operation;
* uses a sensible interval, such as 20–60 seconds;
* marks the connection stale after repeated unanswered requests.

Do not create aggressive polling.

Provide an optional fallback mode that polls get_tip_header only when:

* the WebSocket connection works;
* the node rejects the subscription method;
* the user explicitly enables fallback polling.

Clearly label fallback polling as different from a live subscription.

Security and Browser Limitations

Include a compact help section explaining:

* browsers may block ws:// connections from a page served over HTTPS because of mixed-content rules;
* wss:// may require a valid TLS setup;
* a remote node must expose its WebSocket RPC to the browser;
* firewall and node listening-address settings may block access;
* reverse proxies must support WebSocket upgrades;
* exposing a node RPC publicly can create security and resource-abuse risks;
* users should not expose unrestricted administrative RPC methods to the public internet;
* local static files may have inconsistent browser-origin behavior, so using a small local static server is recommended.

Do not work around browser security restrictions.

Do not disable TLS validation.

Do not embed a public proxy.

Do not send credentials through query strings.

Acceptance Criteria

The implementation is complete only when all of the following work:

1. The user can enter and save a WebSocket node endpoint.
2. The page opens a WebSocket connection.
3. It sends a subscribe request with ["new_tip_header"].
4. It separately shows socket-connected and subscription-active states.
5. It correctly captures the returned subscription ID.
6. It handles subscription results returned as objects or JSON strings.
7. It cycles continuously through mine_0.png to mine_5.png while waiting.
8. It displays mine_found.png on every unique new tip header.
9. It returns to the mining animation after the success display.
10. It deduplicates notifications by block hash.
11. It does not create duplicate timers after reconnection.
12. It displays current block, epoch, timestamp, hash, target, nonce, and related header information.
13. It decodes hexadecimal numeric values without unsafe precision loss.
14. It decodes the packed CKB epoch field.
15. Unsupported optional RPC methods fail gracefully.
16. Automatic reconnection does not create parallel sockets.
17. A deliberate disconnect stops reconnect attempts.
18. Old WebSocket events cannot overwrite a new connection state.
19. The page works on mobile and desktop.
20. Missing images and connection failures produce useful error messages.
21. The browser console remains free of uncaught errors during normal operation.
22. No backend, API proxy, framework, or build step is required.

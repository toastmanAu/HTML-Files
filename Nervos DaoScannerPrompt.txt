Build a polished, mobile-first Nervos DAO portfolio scanner as one complete, self-contained HTML document.

Output only the finished HTML file. Do not include explanations, Markdown fences, setup instructions, pseudocode, TODO comments, omitted sections, placeholders, or additional files.

The application is read-only. It must never request a private key, seed phrase, wallet connection, signature, or transaction approval.

⸻

PURPOSE

Create a browser-based Nervos CKB DAO viewer that allows a user to:

1. Enter one CKB address.
2. Resolve the wallet’s shared User Args/account identifier from that address.
3. Discover DAO Cells belonging to the complete wallet/account represented by those User Args, rather than querying only the exact entered address.
4. Identify all live Nervos DAO positions associated with that wallet.
5. Distinguish:
    * active deposit Cells;
    * phase-one withdrawal Cells;
    * mature withdrawing Cells;
    * immature withdrawing Cells.
6. Calculate and display useful DAO deposit, compensation, maturity and withdrawal information.
7. Use https://mainnet.ckb.dev/rpc as the default RPC endpoint.
8. Allow the user to enter another HTTPS endpoint or a local-node endpoint such as:
    * http://127.0.0.1:8114
    * http://192.168.1.20:8114
9. Operate when opened directly as a local HTML file.

The host HTML viewer provides network access and handles local-file CORS restrictions. Do not add a proxy server or backend requirement.

⸻

IMPORTANT CKB MODEL REQUIREMENTS

Do not model CKB as an account-based blockchain.

CKB uses immutable Cells. A DAO position is represented by a live Cell using the Nervos DAO Type Script.

A CKB address encodes a Lock Script. One wallet/account may control multiple addresses or lock variants. The entered address is only the starting point for resolving the wallet’s User Args.

Do not falsely describe every Cell sharing one exact Lock Script as a complete wallet scan.

The implementation must clearly separate:

* entered address;
* decoded Lock Script;
* extracted or resolved User Args;
* discovered wallet lock scripts or account variants;
* DAO Cells matched to those wallet identifiers.

USER ARGS RESOLUTION AND HONEST FALLBACK

The principal requirement is wallet-wide discovery through User Args, not a single-address lookup.

Implement a WalletIdentityResolver abstraction with clearly separated methods such as:

* decodeEnteredAddress()
* extractUserArgs()
* resolveWalletScripts()
* describeResolutionMethod()
* getResolutionCoverage()

The implementation must use the currently documented User Args mechanism supported by the selected CKB library, indexer, wallet metadata standard or account service.

Do not invent undocumented RPC methods.

The scan workflow must be:

1. Decode the entered address.
2. Validate that its network matches the selected network.
3. Extract the relevant lock information and User Args.
4. Resolve all discoverable Lock Script variants or address records belonging to those User Args.
5. Query DAO Cells across the resolved wallet identity.
6. Deduplicate Cells by tx_hash:index.

Display the actual resolution method used.

Display a coverage badge:

* Wallet-wide — a documented User Args resolver returned wallet/account variants;
* User Args match — Cells were queried through a documented partial-args/User-Args indexer search;
* Single lock only — only the exact decoded Lock Script could be queried;
* Manual address set — the user supplied additional wallet addresses.

If wallet-wide resolution cannot be completed from the entered address and configured endpoints:

* do not silently call the result wallet-wide;
* show a clear limitation;
* retain the exact-address result as a visibly labelled fallback;
* provide an optional textarea allowing the user to paste additional CKB addresses from the same wallet;
* decode, query and deduplicate those addresses;
* never claim that missing addresses have been scanned.

Where the indexer supports partial Script-args matching, use the officially defined prefix/exact matching mode appropriate to User Args. Do not broaden a query in a way that can include unrelated owners.

Show the extracted User Args in shortened form with a copy button and an expandable full-value view.

* query by documented User Args/partial lock-args matching plus DAO Type Script filtering;

DAO STATE CLASSIFICATION

Classify each live DAO Cell according to RFC 0023.

A DAO deposit Cell normally has:

* Nervos DAO Type Script;
* exactly eight bytes of Cell data;
* data equal to eight zero bytes.

A phase-one withdrawal Cell normally has:

* the same DAO Type Script;
* eight-byte little-endian Cell data containing the block number of the original deposit transaction;
* a transaction/header relationship identifying the deposit and withdrawal phases.

Do not classify solely from whether data is zero. Validate all relevant structure available from the RFC and transaction history.

Represent states as:

* deposited;
* withdrawing-immature;
* withdrawing-mature;
* unknown-or-invalid.

If a record cannot be fully verified because a historical transaction or header is unavailable, retain it as partially resolved and show the missing dependency.

DAO CALCULATIONS

Use integer-safe arithmetic with BigInt.

Never calculate capacities, DAO accumulated rates, epoch values or compensation with JavaScript Number where precision could be lost.

Use:

* 1 CKB = 100,000,000 Shannons;
* little-endian decoding for DAO Cell data;
* exact RFC 0023 formulas;
* occupied-capacity treatment required by the DAO rules;
* deposit and withdrawing block headers’ DAO fields;
* correct epoch-number/index/length arithmetic;
* the required DAO lock period and maturity rules;
* proper rounding and integer division.

Prefer an official, maintained CCC DAO helper if it exactly implements the current RFC. Still keep the UI-facing calculation inputs visible for auditability.

For each active deposit, calculate where possible:

* original deposited capacity;
* occupied capacity;
* interest-bearing counted capacity;
* deposit block number;
* deposit epoch;
* deposit timestamp;
* current age in blocks;
* current age in epochs;
* estimated current maximum withdraw capacity;
* estimated accumulated compensation;
* estimated effective annualized return;
* next valid phase-one withdrawal epoch;
* approximate date/time of the next withdrawal window;
* whether phase one can currently be submitted.

For each withdrawing Cell, calculate where possible:

* original deposit block;
* original deposit epoch;
* withdrawal block;
* withdrawal epoch;
* deposit duration;
* locked-in maximum withdraw capacity;
* locked-in compensation;
* required since value;
* maturity epoch;
* remaining epochs;
* approximate remaining time;
* whether phase two is currently mature.

Clearly label time estimates as estimates because epoch duration varies.

Do not display compensation estimates as guaranteed financial returns.

Where current-tip data is insufficient for an exact value, state which value is estimated.
